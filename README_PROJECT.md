Інтерфейс v0.6: графітова тема, новий огляд, швидкі сценарії та розкривні параметри. Розрахункові моделі v0.5 збережено.

**«Стратегія · 90 днів»**: три сценарії роботи після покупки, місткість команди, бюджет усього пакета, календар 13 тижнів, чернетки задач, контроль введеного факту без перезапису плану, імпорт JSON та експорт плану/CSV/HTML. Модель платежів і ручні припущення ефекту дій розділено. Методика й команди: [STRATEGY_90D.md](STRATEGY_90D.md).

Новий розділ **«До купівлі · ML → Порівняння моделей · NN»**: реальний Python-бенчмарк Logistic + Ridge / CatBoost / локальної нейромережі TabPFN v2 на спільних синтетичних даних. Чотири часові групи, калібрування, вибір до фінального тесту, діагностика за продавцями та експорт прогнозів кожної моделі. Інструкція: [MODEL_COMPARISON.md](MODEL_COMPARISON.md); залежності: `requirements-benchmark.txt`; атрибуція: [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

Демонстраційний інструмент для розмови з потенційним роботодавцем про оцінку та придбання портфелів проблемної заборгованості.

## Що показати за п'ять хвилин

1. **Оцінка портфеля.** Назвати граничну ціну, запропоновану ціну, NPV і дохідність. Пояснити, що це наслідок припущень, які видно на екрані.
2. **Затримка.** Зсунути надходження на 3–6 місяців. Сума майбутніх зборів зберігається, але допустима ціна знижується.
3. **Сценарії.** Показати, що базове рішення може не витримати зниження зборів і зростання витрат.
4. **Реєстр.** Відокремити заявлений номінал, задані виключення та вимоги на перевірці.
5. **Прогноз / факт.** Показати незмінний початковий прогноз і синтетичний факт. Завершити коротким інвестиційним висновком.

## Межі

- Усі 1 200 договорів та шість місяців демонстраційного факту є синтетичними. Реальних боржників немає.
- Частки платників, суми погашення за умови платежу та форма кривих — експертні демонстраційні припущення, не оцінена ринкова статистика. Ймовірності однакові в межах сегмента; ранжування не є індивідуальною ML-моделлю. Одиниця аналізу — договір, не унікальний боржник.
- У сценарній оцінці коефіцієнти задані вручну. Окремий модуль «До купівлі · ML» містить навчену на синтетичній історії базову модель; не заявляється її точність для українських реальних портфелів.
- Виключення задані у реєстрі; вони не є автоматичним висновком програми про застосування норм права.
- Податки та боргове фінансування не включені. Модель оцінює unlevered pre-tax cash flows.
- Детальний режим: комісія зборів, команда, IT, накладні, супровід усіх договорів, перевірка, внутрішні операції, заплановані юридичні справи, календар додаткових витрат. Спрощений режим відсотка замінює деталізацію. Подвійного обліку немає.
- Перенесення на дані роботодавця потребує зіставлення полів, юридичної перевірки правил та ретроспективної перевірки на окремих портфелях.

## Запуск

Статичний інтерфейс: з кореня проєкту запустити `python3 -m http.server 8000 --directory dist` та відкрити http://localhost:8000. Для статичного інтерфейсу залежностей немає. Для перенавчання Python-моделі потрібні numpy і scikit-learn.

Розрахунок Python:

```bash
python3 python/valuation.py dist/demo-register.csv --price 3190000 --annual-return 0.60 --cost-rate 0.08
```

Синтетичні дані відтворюються командою `python3 python/generate_demo.py`.

## Перевірка

```bash
python3 -m unittest discover -s tests -v
node tests/test_csv.js
node --check dist/app.js
```

Автоматичні тести перевіряють розподіл витрат між групами, звірку внесків з ціною пакета, касовий дефіцит, витрати без платежів, беззбитковість, разові календарні витрати, стійку окупність, відмову від IRR для потоку з повторними відтоками, звірку номіналу, відсутність подвійних виключень, оцінку за нульової ставки, IRR на граничній ціні, ефект затримки, залежність від ціни та витрат, нульові збори, відхилення некоректних даних і збіг Python/JavaScript.

## CSV

UTF-8, роздільник — кома, десятковий знак — крапка. Поля:

`loan_id,borrower_id,segment,principal,interest,penalty,excluded_amount,dpd,quality`

Сегменти: `bank_early`, `bank_late`, `mfo_early`, `mfo_late`. Статуси: `ready`, `review`. Сегмент задає імпортер; DPD є інформаційним полем, а не автоматичним правилом сегментації. Максимум 50 000 договорів і 20 МБ у браузері. Ідентифікатори мають бути знеособленими.

Імпорт здійснюється у пам'яті браузера без відправлення реєстру серверу. Після оновлення сторінки завантажується вихідний демопортфель.

## Нові екрани v0.2

- **Потенціал вимог:** очікувані платні й безплатіжні договори, середня сума надходжень, поріг беззбитковості, внесок сегментів і ранжування за PV після прямих витрат.
- **Витрати стягнення:** режим обліку, деталізований бюджет, розподіл по всьому пакету, разові витрати із зазначенням місяця.
- **Грошовий потік:** придбання і початкові витрати у моменті 0, наступні місячні потоки, найбільша потреба в капіталі, експорт календаря CSV.

Затримка надходжень подовжує ненульові періоди регулярного бюджету і супроводу; разові події залишаються в заданих місяцях. Множник витрат застосовується лише до майбутніх витрат, один раз. Початкові витрати та ціна не множаться. Після завершення активного бюджету припускаються пасивні надходження без фіксованого бюджету; це відкрите сценарне припущення.

Сценарний розподіл прямих витрат на платників/неплатників виходить із незалежності запланованої юридичної активності та майбутнього платежу; його потрібно замінити фактичною історією. Вимоги review виділені окремо, не називаються неплатниками. Спільні й початкові витрати не розподіляються довільно між договорами.

Зіставлення для перевірки: сума PV внесків усіх договорів − PV спільних витрат − початкові витрати = гранична ціна всього пакета; мінус ціна пакета = NPV. Недисконтований поріг середнього платежу враховує зміну комісії при зміні зборів, за незмінного числа платних договорів і некомісійних витрат.

## Оцінка до покупки v0.3

Новий розділ **«До купівлі · ML»**: прогноз 12-місячної ймовірності й валової суми по договорах на основі історії до дати зрізу; причини відмови від прогнозу; пояснення факторів; відкладений часовий тест; імпорт JSON та експорт CSV. Це окремий прогноз, він не підміняє 36-місячну сценарну оцінку.

Схема та відтворювані команди: [PREPURCHASE_SCHEMA.md](PREPURCHASE_SCHEMA.md).

Демонстраційна історія: 3 320 договорів; 120 неповних спостережень виключені; 64 перетини за позичальниками прибрані з наступних вибірок. Навчання: 1 600; калібрування: 576; незалежний тест: 960. Модель ніколи не використовує тестові цілі для навчання. Поточний пакет містить тільки історію до покупки; майбутній результат для нього відсутній.

Файли: `dist/prepurchase-history.json`, `dist/prepurchase-case.json`, `dist/prepurchase-model.json`, `dist/prepurchase-validation.json`. Вони синтетичні; застосування до іншого файлу не означає перевірену придатність для реального ринку. Для реальної роботи потрібно перенавчити та перевірити модель на дозволених місцевих даних.


Композиція v0.6.1 відтворює затверджений концепт: дії вгорі, чотири KPI, комбінований графік, компактне рішення і два нижніх блоки. Ліва шкала графіка: місячні надходження / витрати (тис. грн); права: баланс після покупки (млн грн), за кінець місяця. Окупність — стійка, недисконтована; IRR збережено в картці рішення. Усі формули й моделі незмінні.


## Карта ризик — дохідність v0.7

Новий розділ порівнює поточну оцінку та зафіксовані знімки грошових потоків. X — зниження NPV у відносному стресі / (ціна + початкові витрати), Y — базова IRR, площа круга — піковий капітал. NPV обчислюється за спільною ставкою. Деталі та формат експорту: `RISK_MAP.md`. Перевірка: `node tests/test_risk.js`.


## Монте-Карло v0.8

Окремий модуль для поточного реєстру: розподіл NPV, поточковий діапазон накопиченого балансу, число платних договорів. Гаусівські спільний і позичальницький фактори, обмежений розкид сум, пов’язані витрати та затримка; витрати всього реєстру збережено. Seed, 500–20 000 симуляцій, зупинка Worker, попередження про застарілий результат, JSON/CSV/HTML. Ймовірності умовні на заданих припущеннях; не відкалібровані на реальному ринку. Окремі показники NPV < 0 та неповернення вкладень. Методика: `MONTE_CARLO.md`. Перевірки: `node tests/test_monte_carlo.js`. Python CLI використовує те саме JS-ядро та потребує Node.js; браузерний запуск не потребує Node чи додаткових бібліотек.
