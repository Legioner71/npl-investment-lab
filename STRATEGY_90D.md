# Сценарна стратегія на 90 днів · v0.5

Модуль формує **чернетку** плану роботи після купівлі портфеля. Він працює локально у браузері або через Python CLI зі спільним JS-ядром. Це сценарний розподіл ресурсів, а не навчена причинна модель дій і не доведений глобальний оптимум. Демонстраційні дані, прогнози й операційні прапорці синтетичні.

## Вхідні дані

1. `case`: той самий формат snapshots / payments, що у [PREPURCHASE_SCHEMA.md](PREPURCHASE_SCHEMA.md). Стан кожного договору на дату зрізу.
2. `operations.accounts`: один необов’язковий операційний запис на договір з `loan_id`, `contact_status` (`allowed`, `blocked`, `unknown`), `rules_verified` (boolean), `active_payment_plan` (boolean), `legal_review_required` (boolean), `updated_at` (YYYY-MM-DD).
3. Прогноз з `horizon_months=12`, `model_id`, `synthetic_training` і масивом `scores`: кожен договір, його дата зрізу, `horizon_end`, статус, P хоча б одного платежу за 12 місяців, умовна сума та очікувана сума. Усі ID і дати звіряються. Потрібна тотожність expected = probability × conditional та bounded amounts. Відмови від прогнозу мають null, не нуль.
4. Параметри планування. UI дозволяє редагувати бюджет, резерв, ставку, часову частку надходжень, місткість і повну вартість команди, комісію, зовнішні витрати, ефект дій, затримки, стрес та контрольні пороги.

Приклад для браузерного імпорту: `dist/strategy-input-demo.json` із ключами `case` та `operations`. Генератор `python/generate_strategy_demo.py` створює операційні прапорці лише для синтетичної демонстрації. Їх не слід сприймати як юридичну перевірку.

На демонстраційному пакеті можна вибрати Logistic + Ridge, CatBoost або TabPFN v2 з зафіксованого benchmark v0.4. Імпорт нового пакета виконує локальний inference базової моделі v0.3; це явно відображається. Синтетично навчена модель потребує перенавчання та незалежної перевірки перед реальним застосуванням. Для нового пакета з TabPFN/CatBoost спочатку отримайте прогноз через Python CLI, потім передайте його планувальнику.

## Межі часу

Горизонт рівно 90 днів; 12 тижнів по 7 днів і останній із 6 днів. Початок не раніше зрізу. Прапорці операцій мають бути відомі не пізніше початку плану. Кінець плану не може виходити за 12-місячний горизонт жодного прогнозу. Після старіння прогнозу його потрібно оновити.

Базові надходження 90 днів = expected_12m × share_90d. За замовчуванням share_90d = 30%. Це **ручне припущення про частку грошей**, не P платежу за 90 днів. Для календаря базові надходження розподілено рівномірно по днях плану. Непідтверджені правові вимоги й неповні дані не отримують нульового прогнозу: base_90d = null; їх можливі надходження не включені до суми. Вартість команди й обліку таких договорів усе одно враховується.

Коли ML-прогноз існує, але новий операційний прапорець вимагає перевірки документів, планувальник консервативно відкладає цей прогноз (`planning_status=legal_hold`). Coverage окремо показує оцінені ML договори й додаткові legal_hold. Це не висновок про юридичну чинність або безнадійність вимоги.

## Напрями

Порядок застосування правил:

1. quality=review, legal_review у прогнозі або legal_review_required → внутрішня перевірка юристом, без завдань контакту та без оцінки надходжень у плані.
2. Відмова від прогнозу → уточнення історії / даних; майбутні гроші не оцінюються.
3. Явний blocked хоча б за одним договором позичальника → жодних контактних завдань за всіма його договорами.
4. Немає операційного запису, allowed або rules_verified → внутрішня перевірка допустимості.
5. Підтверджено allowed, rules_verified і чинну домовленість → чернетка супроводу.
6. Інакше при підтвердженій допустимості → чернетка добровільного врегулювання.

Низька P не є правилом переходу в юридичний напрям. Юридична задача — перевірка документів та варіантів, **не подання позову**. Модуль не змінює чинні графіки платежів і не створює нові зобов’язання сторін.

Фіксовані тривалості завдань у пілоті: супровід 0,25 години оператора; добровільне врегулювання 0,75 години оператора; документи 1 година юриста; дані 0,5 години аналітика; допустимість 0,25 години аналітика. Вони явно збережені у `route_rules` експортованого плану й мають бути адаптовані за реальними нормативами компанії.

Один позичальник має не більше одного контактного завдання на тиждень у цьому плані. Це внутрішня координація чернеток, не висновок про дотримання часових, кількісних чи інших правових вимог. Перед реальною дією працівник перевіряє чинні правила, історію контактів, згоди та обмеження. Продукт не відправляє повідомлень та не здійснює стягнення.

Орієнтири для юридичної адаптації: [Закон України «Про споживче кредитування»](https://zakon.rada.gov.ua/laws/show/1734-19#Text), [Положення НБУ №170](https://zakon.rada.gov.ua/laws/show/v0170500-22#Text). Чинність і застосовність конкретних норм перевіряє юрист; пілот не кодує автоматичний юридичний висновок.

## Ефект і витрати

Для супроводу й добровільного врегулювання задається uplift базових майбутніх зборів. Початок ефекту = кінець тижня завдання + затримка. Додаткові збори = base_90d × uplift × частка 90-денного горизонту, що залишилась після початку ефекту. Сума обмежується залишком basis − base_90d. Гроші розподіляються рівномірно лише після початку ефекту. За межами горизонту ефект не вигадується.

Супровід за замовчуванням: uplift 4%, затримка 7 днів. Урегулювання: uplift 20%, затримка 14 днів. Це непідтверджені припущення, не оцінки впливу, отримані з історії. Вони не описують готові умови знижок чи реструктуризації; працівник погоджує умови окремо. Якщо пропозиція передбачає зменшення погашення, це має бути відображено у валовому прогнозі ефекту. Інформаційним та юридичним перевіркам позитивний ефект у грошах не приписаний.

Повний бюджет = вартість усієї виділеної місткості команди + IT/координація + облік кожного договору + зовнішня вартість завдань + комісія від прогнозних зборів. Виділена команда оплачується повністю, включно з невикористаними годинами; заробітна плата не додається повторно до завдань. Ці ставки мають бути повною вартістю для компанії; якщо певна частина вже включена до іншої статті, параметри потрібно узгодити, щоб уникнути дублювання.

Постійні витрати, місткість і вартість команди пропорційні дням неповного останнього тижня. Договори без платежів і без прогнозу також обслуговуються. Відсоткова комісія врахована один раз. Комісія від невідомих майбутніх зборів не оцінена; бюджет не є гарантією витрат. Резерв залишається невитраченим і **не віднімається** як витрата від NPV чи операційного результату.

Потоки дисконтуються на кінець тижня: PV = flow / (1+annual_discount)^(end_day/365). Ціна покупки вже придбаного портфеля не входить до порівняння операційних стратегій. Показаний операційний результат не є прибутком інвестиції чи окупністю купівлі. Податки, фінансування і решта після 90 днів не включені; 36-місячна DCF лишається окремою.

## Розподіл і порівняння

| Профіль | Операторська місткість, максимум | Частка дозволених добровільних пропозицій, максимум | Мінімальний PV ефекту / зовнішня витрата |
|---|---:|---:|---:|
| Економний | 45% | 35% | 3 |
| Збалансований | 75% | 70% | 1,5 |
| У межах усієї місткості | 100% | 100% | 1 |

Вартість виділеної команди однакова у профілів, навіть якщо використовується менше годин. Спочатку розміщуються внутрішні перевірки (документи першими). Потім чернетки дозволених дій ранжуються за додатковим PV після комісії та зовнішніх витрат на годину. Це жадібна евристика. Враховуються залишок бюджету після резерву, ролі та години, ліміт профілю, координація позичальника й затримка ефекту. Непоміщені завдання залишаються pending, не зникають. Навіть успішний у бюджеті план може мати невиконані внутрішні перевірки, що потребує рішення керівника.

Орієнтир порівняння — найбільший додатковий PV у сценарному стресі серед бюджетно допустимих варіантів, лише якщо він додатний. Стрес за замовчуванням: 80% базових зборів та 50% сценарних додаткових зборів; фіксовані й зовнішні витрати незмінні, комісія перераховується. Це незалежні множники, а не прогноз конкретного макроекономічного сценарію.

Базовий орієнтир без нових дій також включає повну виділену команду, облік і базову комісію. Тому incremental_npv = NPV плану − NPV такого базового орієнтира. Додаткова вартість внутрішніх перевірок врахована, а їх можливі фінансові вигоди поки невідомі. Якщо базового бюджету вже бракує, план показує дефіцит і не додає нових задач. Наявні витрати не обрізаються штучно під ліміт.

## Факт і версії

«Контроль тижня» приймає введені користувачем фактичні збори й витрати. Пороги за замовчуванням: нижче 80% зборів плану або вище 110% витрат плану. Вони породжують позначку необхідності перегляду. Факт зберігається окремо за plan_id і номером тижня та **не переписує** початковий календар. Нові параметри формують новий ID. Сторінка не зберігає дані після перезавантаження; для збереження потрібно експортувати JSON. Автоматичної відправки, регулярних фонових завдань чи автоматичного перепланування немає.

Експорт JSON містить заморожений обраний план, припущення, правила профілю й тривалості, календар, усі рядки й завдання, джерело та окремі введені факти. Короткий ID — стабільний технічний відбиток для версій, не криптографічний підпис. CSV календаря й завдань містять повні списки незалежно від екранних фільтрів. HTML-висновок доступний через кнопку звіту.

## Запуск і перевірка

```bash
python python/generate_strategy_demo.py
python python/prepurchase.py score dist/prepurchase-model.json dist/prepurchase-case.json --output scores.json
python python/strategy.py dist/prepurchase-case.json dist/strategy-operations.json scores.json --output plans.json
# Необов'язкові параметри: --params my-params.json
node tests/test_strategy.js
python -m unittest discover -s tests -p test_strategy_cli.py -v
```

Python-вхід потребує Node.js і викликає той самий `dist/strategy-engine.js`, що браузер. Формули не продубльовані у другій реалізації. Для прогнозу CatBoost/TabPFN використовуйте `python/model_benchmark.py score` із середовища benchmark, потім передайте вихідний JSON у `python/strategy.py`.

Перед реальним застосуванням потрібні дозволені дані компанії, правова перевірка операційних статусів, нормативи трудомісткості, реальний бюджет, модель строків та оцінка причинного впливу дій. Для останньої потрібні журнал дій, результати, витрати і належний дизайн порівняння; зв’язок «дія передувала платежу» сам по собі не встановлює ефект.
