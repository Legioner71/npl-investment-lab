# Модуль Монте-Карло v0.8

Это симуляция взысканий по уже проблемным требованиям. Она не оценивает вероятность дефолта исправно обслуживаемого кредита и не устанавливает конкретных будущих плательщиков. Все распределения демо заданы явно; достоверность для реальных украинских портфелей не заявляется.

## Использование

1. Открыть «Монте-Карло». Источник — текущий реестр и текущие цена, ставка, расходы и параметры сценарной оценки.
2. При необходимости импортировать CSV, проверить сегменты / quality / исключения; задать цену и расходы в «Оцінка портфеля» / «Витрати стягнення».
3. Настроить число запусков, seed и неопределённость. Запустить. Расчёт идёт в Web Worker; интерфейс остаётся доступным, можно остановить расчёт. Старый результат сохраняется до успешного завершения нового.
4. Изучить три графика, два разных риска, P90 капитала, условный срок устойчивой окупаемости, таблицу месячных квантилей. Для точных диапазонов столбцов и месяцев доступны SVG tooltips; месяцы также доступны в таблице.
5. Сохранить JSON (все исходные настройки и результаты без реестра), CSV (по одному исходу на строку и основные параметры) или HTML-отчёт с тремя графиками. Кнопка «Друк / PDF» использует системную печать браузера.

В момент обновления страницы реестр и результат MC сбрасываются. Автосохранения MC в localStorage и импорта результатов MC обратно в интерфейс пока нет. Входные реестры храните отдельно. Если параметры, реестр или настройки MC меняются, результат помечается устаревшим; выгрузка всегда относится к сохранённому запуску, не к новым полям.

Из карты риска кнопка MC доступна для текущего реестра. Сохранённый снимок карты не содержит договоров / borrower_id; для его моделирования требуется загрузить исходный реестр и восстановить полные параметры оценки. Снимки альтернатив не складываются. Ось X карты по-прежнему означает снижение NPV при фиксированном стресс-сценарии / первоначальные вложения; MC её не меняет.

## Вероятности и единица анализа

Исходная `NPL.evaluate` не меняется. Для договора i берутся p_i и условная сумма c_i из её `records`. p_i = min(1, segment.payer × payer_multiplier) для ready с положительной условной суммой; иначе модельных сборов нет.

Опорные сегментные p: bank_early 0.50, bank_late 0.30, mfo_early 0.40, mfo_late 0.25. Это демонстрационные предположения. Для исходных 1200 договоров: ready 1129, review 71, ожидаемые платные договоры 409.15. Review исключены из симуляции сборов, но включены в расходы и показаны отдельно, не названы неплательщиками. Ready с нулевой базой / условной суммой не даёт модельных сборов.

Событие — хотя бы один платёж по договору за полный 36-месячный профиль сборов плюс задержка. Несколько договоров человека — несколько событий с общим фактором borrower_id. Это не число уникальных людей. ML-прогноз на 12 месяцев сюда не подставляется.

## Зависимости

Для каждой симуляции генерируются независимые стандартные нормальные Z_0, Z_b для каждого заёмщика и epsilon_i для договора:

Z_i = sqrt(rho) Z_0 + sqrt((1-rho) tau) Z_b + sqrt((1-rho)(1-tau)) epsilon_i.

Платёж, если Z_i <= Phi^-1(p_i). Значения p=0 и p=1 обрабатываются точно. Маргинальные p_i сохраняются; rho — латентная корреляция разных заёмщиков, rho+(1-rho)tau — латентная корреляция договоров одного заёмщика. Это не корреляции индикаторов платежей. Phi — нормальная CDF, inverse — аппроксимация Acklam, нормальные — Box–Muller, uniform PRNG — Mulberry32. Seed задаётся целым uint32. Это воспроизводимый симулятор, не криптография.

По умолчанию rho=.08, tau=.65. Эти параметры не оценены на истории. Временных режимов, отдельных продавцов, отраслевых / региональных факторов и неопределённости самих p_i пока нет. Для демонстрации p_i фиксированы; MC повторяет случайные исходы, а не переобучает модель.

## Суммы и календарь

Если договор платит: сумма c_i + a_i U[-1,1], a_i = amount_spread × min(c_i, B_i-c_i); B_i — доступная база после исключений. Средняя сумма равна c_i, диапазон [0,B_i]. На границе B_i размах нулевой. Это не «±35% от c_i» при c_i близком к B_i. Индивидуальные размахи условных сумм независимы при фиксированном событии платежа.

Сумма раскладывается по исходной нормированной сегментной кривой w_t proportional to t exp(-(t-1)/scale), t=1…36. Внутридоговорная случайная история отдельных платежей не моделируется; распределение платёжной суммы по месяцам задано этой кривой.

Пусть u=Phi(Z_0). Рост u уменьшает платежи, увеличивает затраты и задержку. Множитель будущих расходов C=1+cost_spread(2u-1), равномерный на [1-cost_spread,1+cost_spread]. Дискретный сдвиг d=floor((2j+1)u)-j; задержка=max(0,min(24,base_delay+d)). На границах 0 / 24 распределение задержки асимметрично. При j=0 календарь фиксирован.

Для каждого возможного значения задержки повторно используется исходный финансовый движок. Ненулевые регулярные расходы подлежат продлению, разовые события остаются в своих месяцах, дополнительные расходы включены один раз. Горизонт — максимальная длина всех вариантов, до 84 месяцев. Потоки не обрезаются; отсутствующие хвостовые расходы дополняются нулями.

В симуляции комиссия = realised_gross × cost_rate × expense_multiplier × C. Остальные будущие расходы = исходные некомиссионные расходы для данного календаря × C. Цена и startup выплачены один раз в t=0 и не умножаются. Детальный / простой режимы сохраняются. Расходы на все ready/review и договоры без платежей сохраняются. После конца активного бюджета допускаются пассивные сборы, как в исходной модели. Налогов и заёмного финансирования нет.

При нулевых размахах суммы, расходов, задержки и вероятностях 0 / 1 результат совпадает с исходным движком. При обычных p средний объём сборов сходится к базе, но средний NPV может отличаться из-за случайных сроков, нелинейности и связанных расходов. Медиана не обязана совпадать со сценарием.

## Выходные показатели

- NPV = -price - startup + sum((gross_t-costs_t)/(1+annual_return)^(t/12)). Потоки в конце месяца.
- **P(NPV < 0)**: не достигнута требуемая ставка, даже если номинальные вложения вернулись.
- **P(капитал не возвращён)**: конечный недисконтированный баланс после покупки, startup и всех расходов < 0 на полном модельном горизонте.
- Численно отрицательными для двух вероятностей считаются значения < -1e-7 грн; это допуск округления, не экономический порог.
- **Капитал** каждой траектории: минус наименьший баланс, включая t=0. Карточка показывает P90 этого показателя. Это не P90 месячных квантилей и не дополнительная сумма сверх цены.
- **Устойчивая окупаемость**: первое пересечение нуля, после которого баланс не опускается ниже нуля. Интерполяция внутри месяца, как в исходном движке. Вероятность окупаемости показана отдельно, срок — условно среди окупившихся. Неокупившиеся не подменяются последним месяцем.
- P05/P10/P50/P90/P95 — линейная интерполяция эмпирических квантилей. Месячные полосы поточковые; это не 90%-й интервал всей траектории. Медианная линия может не соответствовать ни одной конкретной симуляции.
- Средний NPV худших 5%: среднее первых ceil(.05 × draws) отсортированных результатов. Это условный эмпирический tail mean, без заявления о реальном риске.
- У вероятностей показан Wilson 95% интервал для частоты симуляций. Он учитывает только численную ошибку MC при фиксированной модели. Не покрывает ошибку калибровки или пропущенные факторы.

## Настройки и ограничения

По умолчанию: 5000 симуляций, seed=20261030, common_rho=.08, borrower_share=.65, amount_spread=.35, cost_spread=.20, delay_jitter=3. UI: 500…20000 симуляций, API допускает от 1 для точных тестов. rho 0….6; tau / amount_spread 0…1; cost_spread 0….8; jitter целый 0…6. Бюджет вычислений: count × draws <=100 млн. Для реестра 50000 договоров максимум 2000 симуляций за запуск. Данные остаются в браузере; внешних библиотек и сетевой отправки реестров модуль не использует.

Большое число симуляций повышает численную точность, а не достоверность предположений. Для украинского применения нужны разрешённые данные о сборах, датах, действиях / расходах, правовом статусе на дату оценки и зависимостях между договорами, а также отдельная проверка изменений режима рынка. В демо нет автоматической военной / правовой / региональной классификации и определения доступности контакта. Операционные ограничения остаются предметом отдельной проверки и модуля стратегии.

## Локальный запуск и Python

Обычный Windows-запуск `START_WINDOWS.bat` не меняется. Для UI достаточно Python-статического сервера; MC работает внутри браузера, NumPy, GPU и Node не нужны.

Дополнительный CLI Python использует то же JS-ядро и требует установленный Node.js 18+:

```bash
python python/monte_carlo.py dist/demo.json --params mc-params.json --output mc-result.json
```

Пример `mc-params.json`:

```json
{"draws":5000,"seed":20261030,"common_rho":0.08,"borrower_share":0.65,"amount_spread":0.35,"cost_spread":0.2,"delay_jitter":3}
```

Для другого реестра входной JSON: `{"rows":[...],"options":{...}}`; строки соответствуют CSV-схеме, числа JSON numeric. `dist/demo.json` также поддерживается. Прямой Node CLI: `node dist/monte-carlo.js input.json mc-params.json` выводит JSON в stdout. Выгрузка не содержит сырого реестра; для полного повтора нужен исходный файл, параметры и версия ядра.

## Проверка

`node tests/test_monte_carlo.js`: 10 групп проверок — равенство исходному DCF в вырожденном случае (включая late expenses, simple, delay и нулевой дисконт), отсутствие сборов при сохранении затрат, seed / отсутствие мутаций, сохранение маргинальных p / средней ограниченной суммы, эффекты зависимостей, связанный неблагоприятный шок, календарные границы и хвост 84 месяца, разные риски / поздняя потеря окупаемости, интервалы / гистограммы / квантильные полосы / CSV и отбрасывание неверных параметров.

Проверка интерфейса: запуск 5000 симуляций, все три графика, маркировка старого результата, выгрузки JSON и CSV подтверждены. Все 5000 строк CSV сверены с JSON. HTML-отчёт с тремя SVG формируется и показан в диалоге; скачивание HTML в облачном браузере не подтверждено (ожидание события download истекло и для прямой ссылки). Системная печать PDF отдельно не проверялась.
